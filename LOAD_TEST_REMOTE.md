# Load test: deployed instance, measured from outside

Generated by `node scripts/loadsteps.js https://last-seat-sg.onrender.com remote` on 2026-11-14T06:18Z.
Raw summary: [docs/loadtest/remote.json](docs/loadtest/remote.json). Numbers below are copied from it, unedited.

Target: p95 < 200 ms and 0 failed requests.

## Setup

- **Server:** `https://last-seat-sg.onrender.com`, Render free tier in Singapore, exactly as deployed. Nothing was
  raised or switched off. Rate limits, CSRF checks and transactions are all on. The database is MongoDB Atlas M0 in
  Mumbai.
- **Client:** one laptop in India (i7-13620H, Node 25) on a home connection, over the public internet and Cloudflare.
- **Requests:** `GET /api/hackathons/:id/teams`, rotating over three requests: the first page, a page 20 cursors
  deep, and `?skill=design`.
- **Passes:** each step runs 20 s **paced** (each user sends about one request a second, like a person refreshing the
  board) and then 20 s **flat out** (each user sends the next request the moment the last one returns: a stress test).
- **Two latencies per response:**
  - **client** is the full round trip measured on the laptop;
  - **server** is the `app` entry of the response's `Server-Timing` header, the time spent inside the server. See
    [LOAD_TEST_REGIONAL.md](LOAD_TEST_REGIONAL.md).

## Reading it

- **The network sets the floor.** The client p50 is about 85 ms at every load, while the server's p50 is 0.0x ms (a
  cache hit). So about 85 ms of every request is the laptop-to-Singapore round trip, which the code cannot change.
- **100 users at a realistic pace meet the target:** p95 145 ms.
  - The previous measurement (LOAD_TEST_LIVE.md, 2026-11-13) was p95 418 ms. It was made before the board fast path
    started holding concurrent readers on one in-flight query.
- **The 10-user paced p95 is a sampling artefact of connection setup, not load.**
  - Each new HTTPS connection to the service spends 0.45–0.59 s on the TLS handshake. That was measured with
    `curl -w %{time_appconnect}`: 0.484, 0.445, 0.513, 0.483 and 0.590 s.
  - In a 10-user run, 10 of the 197 requests are first connections: 5.1%, exactly where p95 falls.
  - At 50 and 100 users the same 5% contains proportionally fewer handshakes against more requests, and p95 drops to
    143–145 ms.
- **Flat out, the free instance's CPU share is the limit.** The server-side p95 stays under 100 ms. The client p95
  grows because requests queue at the platform's proxy and at the instance's fraction of a CPU.
  - Locally, the same code serves about 7,200 requests a second at 100 connections with p95 21 ms (see
    [PERFORMANCE_AUDIT.md](PERFORMANCE_AUDIT.md)).

## Reproduce

```bash
node scripts/loadsteps.js https://last-seat-sg.onrender.com remote
```

The steps (`LOADTEST_STEPS`), duration (`LOADTEST_DURATION_SECONDS`) and target (`LOADTEST_P95_TARGET_MS`) come from
`.env`, which is validated with zod.
